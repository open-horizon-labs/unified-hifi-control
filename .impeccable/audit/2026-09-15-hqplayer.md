# HQPlayer page audit — 2026-09-15

Scope: the full `/hqplayer` page on deployed build `3ff04ce`, plus the local name-editing change. Live inspection was read-only: playback, routing, saved configuration and pairings were not changed. The rename browser test used synthetic instances on loopback; the integration test used software HQPlayer fixtures.

## Follow-up resolution

All findings below are retained as the original audit record. The follow-up batch implements:

- Desktop configuration profiles: identify a positively reported Desktop product before refusing Embedded-only web requests; the UI explains the distinction without requesting that endpoint. An as-yet unidentified adapter can still initialize its Embedded connection.
- Advanced readback: Desktop 5.35.10 was queried directly and returned `GetJunkFilters result="Error">Unknown command`, while MatrixListProfiles succeeded. Only this typed, exact rejection is treated as an unsupported optional feature; transport errors and other daemon rejections still fail. The response exposes `junk_filters_supported: false`, and supported advanced controls remain available.
- Creation: the Add form sends `create_only: true`; the manager rejects an existing configured ID under its lifecycle lock. Legacy configure requests retain their upsert contract.
- Lazy loading: the DSP body mounts on first expansion, retaining loaded state afterward. Closed instances do not start DSP/profile/advanced reads.
- Touch targets: summaries on the HQPlayer page have a 44px minimum height.
- Destination removal: both the initial button and its confirmation name the destination.
- Pairing: one routing explanation remains, and the empty state asks only for the playback zone.

Production adapter verification against Desktop 5.35.10 completed advanced readback with one matrix profile and `junk_filters_supported=false`; its Embedded profile lane was refused before any HTTP request. Software regression tests also verify that unrelated native errors still fail and create-only requests leave the existing host unchanged. The complete `cargo test --tests --no-fail-fast` suite, `cargo clippy --lib -- -D warnings`, formatting check, and release web build passed. Browser verification against the compiled UI and isolated synthetic API confirmed that Add sends `create_only: true` and displays the 409 conflict, destination removal has a named confirmation and can be cancelled, and only the expanded instance starts DSP reads. At 390px viewport width the page had no horizontal overflow and disclosure rows measured 44px. The browser fixture is UI evidence, separate from the live Desktop read-only adapter check; no NAS configuration or audio route was changed.

## Verdict

The page is recognizably a control application, not a decorative template. Its main weakness is interaction completeness: a connection can be healthy while secondary features fail, and some actions still expose storage semantics instead of the user's intent.

Provisional technical score: **13/20**. This is not a WCAG certification or a performance benchmark.

|---|---:|---|

## Findings

### P0 — Instance name cannot be edited (fixed locally)

Location: `src/app/pages/hqplayer.rs`, `ConfigForm` and `save_config`.

The old input used `disabled: editing || busy`; its value was also the internal instance identifier. Simply unlocking it would feed a new identity into the configure endpoint.

Fix: reuse `/api/zones/name` for a persistent display name. `/hqp/instances` now adds `display_name` while preserving `name`. Name-only edits do not configure/reconnect the engine. Headings, edit/remove labels, pairing labels and DSP error labels use the display name; all routing keeps the stable ID. The NAA-advertised output name remains its separate existing relay setting.

Verification: browser renamed Studio to Music room and showed Saved; the only new mutation was `/api/zones/name` for `hqplayer:Studio`. Integration test asserts unchanged adapter object, instance count, source binding and relay address, plus saved name readback.

### P1 — Profile request fails on the connected Desktop instance

Location: `HqpInstanceDsp` profile resource and `/hqp/instances/{name}/profiles`.

Live evidence: `Profiles unavailable ... HTTP 500: Request failed: 404 Not Found`, while the instance reports connected and native DSP options are available. Users cannot tell whether profiles are unsupported, the web port is wrong, or an endpoint is missing.

Next: verify this Desktop version's profile interface and distinguish unsupported capability from connection/configuration failure. Present an actionable explanation instead of a generic Retry. Suggested pass: `$impeccable harden`.

### P1 — Advanced DSP readback times out

Location: `HqpInstanceDsp`, `refresh_advanced_projection` and the scoped matrix/profiles endpoint.

Live evidence: `HQPlayer accepted the command but did not publish a verified readback in time`. The page still shows basic native options but cannot deliver the advanced panel. This audit establishes the failure, not its native-protocol cause.

Next: trace the failed refresh through command admission, native response and aggregator publication for this Desktop build. Suggested pass: `$impeccable harden` after the backend diagnosis.

### P1 — Add can update an existing identity

Location: `save_config` and `HqpInstanceManager::configure_unique_instance`.

Code evidence: Add and Edit both call configure. The duplicate-address check skips the same instance name; `get_or_create_locked(name)` returns the existing instance and `configure(...)` changes it. A user adding a new connection with an existing internal name can update that connection instead. This was not exercised against the live system.

Next: make create versus update explicit and reject existing IDs during creation. Preserve the existing API's update compatibility while giving the Add UI an unambiguous create path. Suggested pass: `$impeccable harden`.

### P2 — Secondary reads happen before the user opens DSP

Location: `HqpInstanceDsp` resources and initial advanced refresh.

Each configured instance starts the same secondary requests on mount. With several instances, this creates unnecessary work and reports failures for panels the user has not requested.

Next: load profiles and advanced settings on first expansion, retain successful state, and offer explicit retry. Keep lightweight playback/status fresh independently. Suggested pass: `$impeccable optimize`.

### P2 — Disclosure targets are small

Location: Paired source, relay configuration/settings, DSP and Connection settings summaries.

Measured heights are 20–24px. Native semantics and keyboard expansion are present, but touch selection is unnecessarily precise. This is a design-target finding; spacing exceptions were not evaluated for a formal WCAG 2.5.8 judgment.

Next: increase the clickable row height to at least 44px without increasing copy. Suggested pass: `$impeccable adapt`.

### P2 — Destination removal lacks a destination-specific accessible name

Location: `src/app/components/hqp_outputs.rs`, saved destination actions.

Live accessibility tree exposes two buttons named only Remove; Select and Edit already include their destination names. Screen-reader button navigation loses which route will be removed.

Next: label each Remove action with its destination and retain the existing named confirmation. Suggested pass: `$impeccable harden`.

### P2 — Pairing repeats instructions and asks for an already-chosen instance

Location: `HqpInstancePairing` and `ZoneLinkTable`.

The outer disclosure explains pairing versus routing; the nested table repeats that warning and says to choose an HQPlayer instance even though the user is already inside one and the selector is hidden.

Next: keep one explanation and use instance-specific empty-state copy. Suggested pass: `$impeccable clarify`.

## What works

- Each configured engine has its own semantic region and controls.
- Product and full reported engine version are visible.
- Selected route is not presented as proof of audio; the live page says No audio confirmed.
- Native selects and explicit labels keep DSP controls operable without custom widgets.
- Connection editing sits below day-to-day controls; removal has a named confirmation.
- Name changes reuse saved zone naming instead of rebuilding identities.

## Coverage and limits

Inspected playback, pairing, relay summary/destination list, DSP, connection form, loading/error states and narrow layout. Mutating live audio, live deletion, live pairing and network-wide discovery were deliberately not exercised. No findings from the bundled detector on the two Rust files; its HTML/CSS-oriented rules do not establish clean Dioxus output. Light themes, screen-reader traversal, 200% text scaling, and performance timings remain unverified.

The original recommended work is implemented in the follow-up batch above. The broader unverified accessibility/performance coverage remains a testing limit, not a newly discovered defect.
